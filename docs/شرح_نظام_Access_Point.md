# 🎓 شرح نظام Access Point - نظام تسجيل الحضور الذكي

## نظرة عامة على الفكرة

تخيل إن عندك قاعة محاضرات في الكلية وعاوز تسجل حضور الطلاب **تلقائياً** من غير ما حد يعمل أي حاجة يدوي. الحل هو إننا نستخدم **نقطة وصول لاسلكية (Access Point)** متصلة بالنظام:

- الطالب **يدخل القاعة ← موبايله يتصل بالشبكة ← النظام يسجل حضوره تلقائي**
- الطالب **يسيب القاعة ← موبايله يقطع ← النظام يسجل وقت خروجه**

> [!IMPORTANT]
> الـ Access Point هنا مش Router عادي - ده **لابتوب بيشغل Mobile Hotspot** وعليه سكريبت بيراقب مين متصل ومين قطع، وبيبعت المعلومات دي للسيرفر.

## 🔧 مكونات النظام

### 1. الـ Access Point (السكريبت على اللابتوب)

ده ملف Python اسمه `access_point.py` بيشتغل على اللابتوب اللي بيعمل Hotspot في القاعة.

### 2. السيرفر (Backend API)

ده Node.js Server بيستقبل الأحداث (Events) من الـ Access Point ويعالجها.

### 3. قاعدة البيانات (MongoDB)

بتخزن بيانات الطلاب والقاعات والمحاضرات وسجلات الحضور.

## 🔄 دورة حياة النظام كاملة (Full System Lifecycle)

### المرحلة 1: الإعداد والتشغيل (Setup)

```
المسؤول (Admin)                         قاعدة البيانات
    │                                       │
    │  1. يضيف قاعة (Hall) باسم مثلاً      │
    │     "قاعة 101"                        │
    │     مع AP Identifier = "AP_101"       │
    ├──────────────────────────────────────►│
    │                                       │
    │  2. يضيف المحاضرات ومواعيدها         │
    │     (كل محاضرة مربوطة بقاعة معينة)   │
    ├──────────────────────────────────────►│
    │                                       │
    │  3. يسجل الطلاب وأجهزتهم            │
    │     (كل طالب له MAC Address)          │
    ├──────────────────────────────────────►│
    │                                       │
```

**التجهيز على اللابتوب:**
1. المسؤول يفتح **Mobile Hotspot** على اللابتوب (Windows)
2. شبكة الهوتسبوت الافتراضية في Windows بتشتغل على نطاق `192.168.137.x`
3. يشغّل السكريبت `python access_point.py`

**الإعدادات الأساسية في السكريبت:**

| الإعداد | القيمة | الشرح |
|---------|--------|-------|
| `AP_IDENTIFIER` | `"AP_101"` | المعرّف الفريد للقاعة - لازم يكون نفس القيمة المسجلة في قاعدة البيانات |
| `SUBNET` | `"192.168.137."` | نطاق الـ IP الافتراضي لـ Windows Mobile Hotspot |
| `THREAD_COUNT` | `50` | عدد الـ Threads المتوازية في عملية الفحص (Scan) |
| `MAX_MISSED_PINGS` | `30` | عدد مرات الفحص الفاشلة قبل ما يعتبر الجهاز قطع الاتصال |
| `SCAN_INTERVAL` | `4` ثواني | الفترة بين كل عملية فحص والتانية |
| `BACKEND_URL` | `"http://localhost:5000/api"` | عنوان السيرفر |
| `AP_API_KEY` | مفتاح سري | مفتاح التوثيق عشان السيرفر يتأكد إن الطلب جاي من Access Point حقيقي |
| `HEARTBEAT_INTERVAL` | `60` ثانية | كل 60 ثانية بيبعت إشارة "أنا شغال" للسيرفر |

### المرحلة 2: فحص الشبكة (Network Scanning)

دي أهم عملية في الـ Access Point. بتحصل كل **4 ثواني** وبتمر بالخطوات دي:

#### الخطوة 1: مسح الشبكة (Ping Sweep)

```
السكريبت بيعمل Ping لكل IP في النطاق 192.168.137.2 → 192.168.137.254
(253 عنوان IP محتمل)

┌─────────────────────────────────────────────────────────┐
│                    Ping Sweep Process                     │
│                                                          │
│  Thread 1:  ping 192.168.137.2   → Reply? ✅ أو ❌       │
│  Thread 2:  ping 192.168.137.3   → Reply? ✅ أو ❌       │
│  Thread 3:  ping 192.168.137.4   → Reply? ✅ أو ❌       │
│  ...                                                     │
│  Thread 50: ping 192.168.137.51  → Reply? ✅ أو ❌       │
│                                                          │
│  (بيشتغل 50 Thread في نفس الوقت للسرعة)                │
│  (بعد ما الـ 50 يخلصوا، يبدأ الـ 50 اللي بعدهم)       │
└─────────────────────────────────────────────────────────┘
```

**إزاي الـ Ping بيشتغل؟**
- بيبعت **ICMP Echo Request** لكل عنوان IP
- لو الجهاز موجود ومتصل بالشبكة → بيرد بـ **ICMP Echo Reply** (يعني "Reply from")
- لو مفيش جهاز ← ما بيردش (Timeout بعد 500 ميلي ثانية)
- بيستخدم الأمر: `ping -n 1 -w 500 <IP>`
  - `-n 1`: إرسال Ping واحد بس
  - `-w 500`: الانتظار 500 ميلي ثانية كحد أقصى

**ليه بيستخدم Multi-threading؟**
- لو عمل Ping لكل IP واحد ورا التاني = 253 × 500ms = **دقيقتين** لكل فحص!
- باستخدام 50 Thread في نفس الوقت = **بيخلص في ثواني قليلة**

#### الخطوة 2: استخراج الـ MAC Address (ARP Lookup)

```
بعد ما يعرف الـ IP اللي موجودة على الشبكة، بيدور على الـ MAC Address بتاع كل واحد

┌─────────────────────────────────────────────────────────┐
│                   ARP Table Lookup                        │
│                                                          │
│  الأمر: arp -a                                           │
│                                                          │
│  النتيجة:                                                │
│  ┌──────────────────────────────────────────────┐        │
│  │ Internet Address    Physical Address    Type  │        │
│  │ 192.168.137.5      A4-B1-C2-D3-E4-F5  dynamic│       │
│  │ 192.168.137.12     B8-27-EB-AA-BB-CC  dynamic│       │
│  └──────────────────────────────────────────────┘        │
│                                                          │
│  السكريبت بيقرأ الجدول ده ويطلع الـ MAC لكل IP         │
│  وبيحوله لصيغة موحدة: A4:B1:C2:D3:E4:F5                │
└─────────────────────────────────────────────────────────┘
```

**شرح الـ ARP Table:**
- الـ ARP (Address Resolution Protocol) هو بروتوكول بيربط بين الـ **IP Address** والـ **MAC Address**
- كل جهاز متصل بالشبكة بيكون موجود في الـ ARP Table
- لما نعمل Ping لجهاز، الـ Operating System بيضيفه تلقائي في الـ ARP Table
- السكريبت بيقرأ الـ ARP Table بالأمر `arp -a` ويستخرج الـ MAC من كل سطر

**ليه الـ MAC Address مهم؟**
- الـ **IP Address بيتغير** كل مرة الجهاز يتصل (DHCP بيديله IP مختلف)
- الـ **MAC Address ثابت** لكل جهاز ← ده اللي بنعرّف بيه الطالب

### المرحلة 3: تتبع الأجهزة (Device Tracking)

السكريبت بيحتفظ بقائمة في الذاكرة فيها كل الأجهزة المتصلة حالياً:

```
device_tracker = {
    "192.168.137.5": {
        "mac": "A4:B1:C2:D3:E4:F5",     ← الـ MAC Address بتاع الموبايل
        "missed": 0,                      ← عدد مرات ما لقيناش الجهاز
        "check_in": "2024-03-15 09:05",   ← وقت أول اتصال
        "sent_to_server": True             ← هل بلّغنا السيرفر؟
    },
    "192.168.137.12": {
        "mac": "B8:27:EB:AA:BB:CC",
        "missed": 3,
        "check_in": "2024-03-15 09:10",
        "sent_to_server": True
    }
}
```

#### السيناريو 1: جهاز جديد اتصل (New Device Connected) 🟢

```
┌───────────┐    فحص الشبكة    ┌──────────────┐
│  📱 موبايل │ ◄═══════════════ │  💻 Access    │
│  الطالب   │  Ping → Reply ✅ │    Point      │
└───────────┘                   └──────┬───────┘
                                       │
                    1. الـ IP مش موجود في القائمة
                    2. يعمل ARP Lookup → يجيب الـ MAC
                    3. يضيف الجهاز في device_tracker
                    4. يطبع: [+] JOINED | IP: 192.168.137.5 | MAC: A4:B1:C2:D3:E4:F5
                    5. يبعت Event للسيرفر (device-connected)
                                       │
                                       ▼
                              ┌──────────────────┐
                              │  🖥️ السيرفر       │
                              │                  │
                              │  POST /event     │
                              │  {               │
                              │   eventType:     │
                              │    "device-      │
                              │     connected",  │
                              │   macAddress:    │
                              │    "A4:B1:...",  │
                              │   apIdentifier:  │
                              │    "AP_101"      │
                              │  }               │
                              └──────────────────┘
```

#### السيناريو 2: جهاز لسه متصل (Still Connected) 🔵

```
الجهاز اللي كان موجود لسه بيرد على الـ Ping
    ↓
السكريبت بيعمل Reset لعداد الـ "missed" → يرجعه 0
    ↓
لو الإرسال للسيرفر كان فشل قبل كده (sent_to_server = False)
    ↓
بيحاول يبعت تاني (Retry Mechanism)
```

#### السيناريو 3: جهاز قطع الاتصال (Device Disconnected) 🔴

```
┌─────────────────────────────────────────────────────────────┐
│                  آلية اكتشاف قطع الاتصال                     │
│                                                              │
│  Scan 1: 192.168.137.5 مش موجود → missed = 1               │
│  Scan 2: 192.168.137.5 مش موجود → missed = 2               │
│  Scan 3: 192.168.137.5 مش موجود → missed = 3               │
│  ...                                                         │
│  Scan 30: 192.168.137.5 مش موجود → missed = 30             │
│                                                              │
│  ⚠️ missed >= MAX_MISSED_PINGS (30)                         │
│  ↓                                                           │
│  ✅ الجهاز فعلاً قطع ← يبعت "device-disconnected" للسيرفر  │
│  ✅ يشيل الجهاز من القائمة                                   │
│  ✅ يحسب مدة التواجد (Duration)                              │
└─────────────────────────────────────────────────────────────┘
```

**ليه بنستنى 30 مرة فحص (وليس مرة واحدة)؟**

> [!TIP]
> 30 مرة فحص × 4 ثواني بين كل فحص = **دقيقتين تقريباً** قبل ما نقرر إن الطالب مشي فعلاً.
> ده عشان ممكن يحصل:
> - **فقدان مؤقت للإشارة** ← الموبايل مرد على Ping واحد بس بيرجع بعدها
> - **الطالب بعيد شوية عن الـ Hotspot** ← الإشارة ضعيفة لكن لسه متصل
> - **ازدحام على الشبكة** ← الـ Ping ضاع لكن الاتصال لسه قائم
>
> لو سجلنا القطع من أول مرة، هيكون عندنا **False Disconnections كتير**.

### المرحلة 4: معالجة الأحداث في السيرفر (Server-Side Processing)

لما السيرفر يستقبل حدث (Event) من الـ Access Point، بتحصل سلسلة عمليات:

#### أولاً: التحقق من الهوية (Authentication)

```
┌──────────────────────────────────────────────────────────────┐
│                    Middleware: verifyAccessPoint               │
│                                                               │
│  1. السيرفر بيشوف هل الـ Request فيه Header اسمه:           │
│     X-API-Key                                                 │
│                                                               │
│     ❌ لو مفيش → يرفض الطلب (401 Unauthorized)               │
│     ✅ لو موجود → يكمل                                       │
│                                                               │
│  2. بيقارن الـ API Key بالمفتاح السري المخزّن عنده:          │
│                                                               │
│     ❌ لو مش متطابق → يرفض الطلب (401 Unauthorized)          │
│     ✅ لو متطابق → بيدور على القاعة (Hall) في قاعدة          │
│        البيانات باستخدام الـ apIdentifier                     │
│                                                               │
│  3. بيحدّث حالة الـ AP:                                      │
│     - isOnline = true                                         │
│     - lastSeen = الوقت الحالي                                 │
│                                                               │
│  ده بيخلي لوحة التحكم (Dashboard) تعرف إن الـ AP شغال      │
└──────────────────────────────────────────────────────────────┘
```

> [!NOTE]
> **ليه بنستخدم API Key وليس Username/Password؟**
> لأن الـ Access Point هو جهاز (Machine-to-Machine communication) مش مستخدم بشري.
> الـ API Key بيكون أبسط وأنسب في الحالة دي.

#### ثانياً: تحديد القاعة (Hall Identification)

```
السيرفر بيدور على القاعة بالترتيب ده:
    │
    ├─ 1. بالـ apIdentifier (مثلاً "AP_101")
    │      ↓
    │      بيبحث في جدول Halls عن:
    │      accessPoint.apIdentifier == "AP_101"
    │      ↓
    │      لقاها؟ ← "قاعة 101" ✅
    │
    ├─ 2. لو ما لقاش → بيدور بالـ MAC Address بتاع الـ AP نفسه
    │
    └─ 3. لو ما لقاش → بيستخدم القاعة اللي الـ Middleware حطها
         │
         └─ لو برضو ما لقاش ← خطأ 404: "Access Point not registered"
```

#### ثالثاً: تسجيل الحدث (Connection Log)

```
بغض النظر عن النتيجة، كل حدث بيتسجل في جدول ConnectionLog:

┌──────────────────────────────────────┐
│           Connection Log              │
├──────────────────────────────────────┤
│ macAddress:  "A4:B1:C2:D3:E4:F5"    │
│ hall:        "قاعة 101"             │
│ eventType:   "device-connected"      │
│ timestamp:   "2024-03-15 09:05:30"   │
│ processed:   false → true            │
│ processingResult: "نتيجة المعالجة"  │
└──────────────────────────────────────┘
```

> [!TIP]
> كل الأحداث بتتسجل حتى لو الطالب مش معروف. ده مفيد عشان:
> - **تتبع الأخطاء** ← لو طالب اشتكى إنه كان حاضر
> - **إعادة المعالجة** ← الأدمن يقدر يعيد معالجة الحدث بعد ما يسجل الـ MAC

#### رابعاً: تحديد هوية الطالب (Student Identification)

```
السيرفر بياخد الـ MAC Address وبيدور على الطالب صاحبه:

MAC Address: "A4:B1:C2:D3:E4:F5"
                │
                ▼
    ┌───────────────────────────────────────────┐
    │  البحث بالترتيب:                          │
    │                                           │
    │  1. MAC Address + الجهاز متحقق منه ✅     │
    │     (isVerified = true)                    │
    │     ↓                                     │
    │     لقاه؟ ← الطالب أحمد محمد            │
    │                                           │
    │  2. لو ما لقاش ← يدور بالـ MAC بدون     │
    │     شرط التحقق                            │
    │     (للأجهزة اللي الأدمن سجلها يدوياً)    │
    │                                           │
    │  3. لو ما لقاش ← يدور بالـ Device ID     │
    │     (خطة بديلة)                           │
    │                                           │
    │  4. لو ما لقاش خالص ←                    │
    │     "الحدث اتسجل بس مفيش طالب مربوط"     │
    └───────────────────────────────────────────┘
```

**إزاي الطالب بيسجل الـ MAC Address بتاعه؟**
- الطالب بيسجل من خلال تطبيق الموبايل
- التطبيق بياخد الـ MAC Address أو Device ID من الموبايل تلقائي
- بيتبعت للسيرفر ويتخزن مع بيانات الطالب

### المرحلة 5: تسجيل الحضور (Attendance Recording)

دي المرحلة الأهم - لما نعرف مين الطالب وفي أنهي قاعة، بنسجله حضور.

#### عند الاتصال (device-connected):

```
┌────────────────────────────────────────────────────────────────────┐
│                     handleConnect - خطوات التنفيذ                   │
│                                                                    │
│  1. إنشاء/تحديث جلسة الطالب (Student Session)                    │
│     ┌──────────────────────────────────────┐                      │
│     │ Student Session                       │                      │
│     │ ─────────────────                     │                      │
│     │ student:     "أحمد محمد"             │                      │
│     │ currentHall: "قاعة 101"              │                      │
│     │ macAddress:  "A4:B1:C2:D3:E4:F5"     │                      │
│     │ connectedAt: "09:05:30"              │                      │
│     │ isActive:    true                     │                      │
│     └──────────────────────────────────────┘                      │
│                                                                    │
│  2. البحث عن محاضرة نشطة في القاعة                               │
│     ┌──────────────────────────────────────┐                      │
│     │ هل فيه محاضرة دلوقتي في القاعة؟     │                      │
│     │                                       │                      │
│     │ السيرفر بيشوف:                        │                      │
│     │ • اليوم = السبت (dayOfWeek = 6)       │                      │
│     │ • الوقت الحالي = 09:05                │                      │
│     │ • فيه محاضرة من 09:00 لـ 10:30؟       │                      │
│     │                                       │                      │
│     │ ✅ نعم ← محاضرة "هندسة الشبكات"      │                      │
│     │ ❌ لا  ← مفيش محاضرة (الحدث يتسجل بس)│                      │
│     └──────────────────────────────────────┘                      │
│                                                                    │
│  3. التحقق من التسجيل في المادة                                   │
│     ┌──────────────────────────────────────┐                      │
│     │ هل الطالب "أحمد" مسجل في مادة        │                      │
│     │ "هندسة الشبكات"؟                      │                      │
│     │                                       │                      │
│     │ ✅ نعم ← نسجله حضور                   │                      │
│     │ ❌ لا  ← الحدث يتسجل بس مش حضور      │                      │
│     └──────────────────────────────────────┘                      │
│                                                                    │
│  4. إنشاء سجل الحضور (Attendance Record)                          │
│     ┌──────────────────────────────────────┐                      │
│     │ Attendance Record                     │                      │
│     │ ─────────────────                     │                      │
│     │ student:  "أحمد محمد"                │                      │
│     │ course:   "هندسة الشبكات"            │                      │
│     │ lecture:  "المحاضرة 5"               │                      │
│     │ hall:     "قاعة 101"                 │                      │
│     │ date:     "2024-03-15"               │                      │
│     │ status:   "in-progress" ⏳            │                      │
│     │ sessions:                             │                      │
│     │   - checkIn: "09:05:30"              │                      │

│  5. ربط الجلسة بسجل الحضور                                       │
```

> [!IMPORTANT]
> الطالب ممكن يدخل ويخرج أكتر من مرة خلال المحاضرة الواحدة.
> النظام بيتعامل مع ده بذكاء:

```
سيناريو: الطالب أحمد في محاضرة من 9:00 لـ 11:00

09:05 ← دخل القاعة (device-connected)
       Session 1: checkIn = 09:05

09:45 ← خرج يشرب مية (device-disconnected)
       Session 1: checkIn = 09:05, checkOut = 09:45
       duration = 40 دقيقة
       status = present

10:00 ← رجع تاني (device-connected)
       Session 2: checkIn = 10:00
       status = in-progress (اتفتح تاني)

10:50 ← المحاضرة خلصت وخرج (device-disconnected)
       Session 2: checkIn = 10:00, checkOut = 10:50
       duration = 50 دقيقة

التقرير النهائي:
┌─────────────────────────────────────────┐
│  إجمالي وقت التواجد = 40 + 50 = 90 دقيقة │
│  مدة المحاضرة = 120 دقيقة               │
│  نسبة الحضور = 90/120 = 75%             │

```

## 💓 نظام الـ Heartbeat (نبضات القلب)

```
كل 60 ثانية، الـ Access Point بيبعت إشارة للسيرفر:

Access Point                          السيرفر
    │                                    │
    │  POST /api/connections/event       │
    │  {                                 │
    │    eventType: "heartbeat",         │
    │    macAddress: "00:00:00:00:00:00",│  ← MAC وهمي (مش جهاز حقيقي)
    │    apIdentifier: "AP_101"          │
    │  }                                 │
    ├───────────────────────────────────►│
    │                                    │
    │         200 OK ✅                  │
    │◄───────────────────────────────────┤
    │                                    │
    │  السيرفر بيحدّث:                  │
    │  • accessPoint.isOnline = true     │
    │  • accessPoint.lastSeen = now      │
    │                                    │
```

**ليه الـ Heartbeat مهم؟**

| الفايدة | الشرح |
|---------|-------|
| **معرفة حالة الـ AP** | لوحة التحكم بتعرض هل الـ AP شغال ولا لا |
| **اكتشاف المشاكل** | لو الـ AP وقف عن إرسال Heartbeat، يعني فيه مشكلة |
| **اختبار الاتصال** | عند بداية التشغيل، أول Heartbeat بيتأكد إن السيرفر شغال |

**ماذا لو السيرفر مش شغال؟**
- السكريبت بيشتغل في **وضع Offline** ← بيفحص الشبكة عادي ويطبع النتائج
- لما السيرفر يرجع يشتغل ← بيحاول يبعت الأحداث المعلقة (Retry)

## 🌐 بروتوكول الاتصال (Communication Protocol)

### الطلب (Request) من الـ Access Point للسيرفر:

```
POST /api/connections/event HTTP/1.1
Host: localhost:5000
Content-Type: application/json
X-API-Key: MySuperSecretKey2024

{
    "eventType": "device-connected",       ← نوع الحدث
    "macAddress": "A4:B1:C2:D3:E4:F5",    ← MAC الموبايل
    "apIdentifier": "AP_101",              ← معرّف القاعة
    "timestamp": "2024-03-15T09:05:30"     ← وقت الحدث
}
```

### الرد (Response) من السيرفر:

```json
{
    "success": true,
    "message": "Connection event processed",
    "data": {
        "student": "20201234",
        "hall": "قاعة 101",
        "eventType": "device-connected"
    }
}
```

### أنواع الأحداث (Event Types):

| الحدث | القيمة | المعنى |
|-------|--------|--------|
| اتصال جهاز | `device-connected` | موبايل طالب اتصل بالشبكة |
| قطع جهاز | `device-disconnected` | موبايل طالب قطع الاتصال |
| نبضة قلب | `heartbeat` | الـ AP بيقول "أنا شغال" |

## 🔄 آلية إعادة المحاولة (Retry Mechanism)

```
┌──────────────────────────────────────────────────────────────────┐
│              ماذا يحصل لو السيرفر مش متاح؟                      │
│                                                                   │
│  الفحص الأول:                                                    │

│                                                                   │
│  الفحص التاني (بعد 4 ثواني):                                    │
│  ├─ الجهاز لسه موجود                                            │

│  ├─ حاول يبعت للسيرفر ← فشل ❌                                  │
│  └─ sent_to_server لسه false                                     │
│                                                                   │
│  الفحص التالت:                                                   │
│  ├─ الجهاز لسه موجود                                            │

│  └─ sent_to_server = true ← مش هيحاول تاني                      │
│                                                                   │
│  ═══════════════════════════════════════════                      │
```

## ⚠️ التعامل مع الحالات الاستثنائية

| الحالة | ماذا يحصل |
|--------|-----------|
| **الموبايل مش متصل بالـ WiFi** | النظام مش هيشوف الطالب ← يتسجل غياب |
| **الموبايل متصل بس MAC مش مسجل** | الحدث يتسجل في الـ Log بس مش بيأثر على الحضور |
| **مفيش محاضرة في الوقت ده** | الحدث يتسجل بس مش بيعمل سجل حضور |
| **الطالب مش مسجل في المادة** | الحدث يتسجل بس الحضور مش بيتسجل |
| **السيرفر واقع** | السكريبت يشتغل Offline ويحاول يبعت لما السيرفر يرجع |
| **الإشارة ضعيفة (Ping فاشل مؤقت)** | النظام بيستنى 30 فحص قبل ما يقرر إن الطالب قطع |
| **الطالب خرج ورجع** | بيتعمل Session جديدة وبتتضاف لسجل الحضور |
